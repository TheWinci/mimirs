# Descry and the 11-minute Kubernetes index

Inspected on 2026-09-07. Descry commit [f0a4966](https://github.com/jKiler/descry/tree/f0a4966b71c25db7d016c9885121fad34d97382d), including its ten published commits. External codesearch-bench commit [94fee7e](https://github.com/jKiler/codesearch-bench/tree/94fee7e1cdf249591e711f4c8fdc3ebfff60af35).

The published implementation makes 11 minutes plausible, but does not establish which combination produced that result. The user has confirmed q8 and three CPUs for the reported run. Those match our configured model-thread budget and model export, so neither higher worker count nor quantization explains this comparison. The user dates the result to July 21. The first public commit on July 26 uses the declaration chunker; tree-sitter was introduced in a commit authored August 1 and committed August 2. The older declaration design is therefore the strongest historical inference, and its substantially smaller embedding workload is the leading explanation. Otherwise hardware, ONNX Runtime version and session sharing remain unmeasured candidates. Current Descry's tree-sitter chunker does more model work than Mimirs on our frozen corpus. There is no evidence here that Go itself explains the difference.

The user reports an Apple M3, q8 model and three CPUs for the 11-minute run. The author used all CPUs at an earlier point, but that does not describe this timed result. The message reporting the result is dated July 21, before the first public commit. The exact M3 variant, command, private July 21 implementation, ONNX Runtime version, cache state and timing scope remain unknown. We treat three CPUs as three embedding workers unless a command shows another form of CPU limit. Neither inspected repository publishes the 11-minute run log. Our measured reference remains 1,219.085 seconds on an Apple M2 Pro with three inference workers. No new full indexing benchmark was run for this analysis.

## What the July 21 date establishes

The [first public commit](https://github.com/jKiler/descry/commit/f68c9a9839a83709f4f084bac81c9700574b3ca5), authored and committed July 26, constructs `chunk.NewASTChunker()` directly and truncates model inputs at 256 tokens. The [tree-sitter introduction](https://github.com/jKiler/descry/commit/f0a4966b71c25db7d016c9885121fad34d97382d) was authored August 1 and committed August 2. A result reported July 21 most likely belongs to the older declaration design, not the current tree-sitter workload. The public history begins after the message, so this is a strong inference, not verification of the exact timed source. Private experiments, an earlier runtime and different corpus selection remain possible.

## CPU scheduling and session ownership

Descry creates `min(GOMAXPROCS, chunk_count)` goroutines. Each claims the next chunk through an atomic counter and embeds it. It explicitly sets ONNX intra-op threads to one. The CLI constructs one OrtEmbedder, so these workers invoke the same ONNX session concurrently with separate tensors. See [worker loop](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/index/index.go#L216-L252), [session construction](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/embed/ort.go#L50-L115), and [CLI wiring](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/cmd/descry/main.go#L282-L296). The local audit resolved GOMAXPROCS to ten; this says nothing about the author's timed setting.

Mimirs defaults to one third of available CPUs, which selected three on our ten-CPU host. It owns one single-threaded session per worker. Our existing controlled replay found six workers gave 1.966 times the throughput of three with byte-identical sample vectors. Full six-worker development indexes also preserved every published table and vector. See [runtime experiment](../runtime/RUNTIME.md), [worker configuration](../../../src/config.rs), and [pool](../../../src/embedding/pool.rs).

This evidence supports testing Kubernetes with six workers as a way to improve our time. It does not explain the friend's reported three-CPU result, and does not prove a six-worker Kubernetes time. Shared-session execution is a separate candidate, particularly for reducing memory per additional worker; its throughput and vector equality are unmeasured in Mimirs. A lock held around the full Run call would serialize inference and defeat that experiment.

## Counted embedding work on our exact corpus

Both Descry modes below use the current commit, with `ast-go` selecting the older declaration strategy. This is not a replay of a historical binary. The current walker accepts 8,749 of our 8,790 frozen Go files. It excludes 41 fixture files under testdata, totaling 9,117 bytes, only 0.013% of the corpus bytes. No additional generated-file, size or vendor exclusions occurred in this audit. Every original file hash was verified against our frozen manifest before saving the results.

| Workload | Stored vectors or emitted chunks | Unique model inputs | Input tokens sent to model |
| --- | ---: | ---: | ---: |
| Mimirs Rust, current TS v2 policy | 134,363 vectors | 186,240 windows | 29,437,506 |
| Descry, declaration `ast-go` mode | 105,995 chunks | 105,993 texts | 15,144,432 |
| Descry, current default `ts` mode | 254,593 chunks | 252,980 texts | 45,317,443 |

Mimirs windows follow actual production splitting and deduplication within each file's 1,024-document groups. Descry unique inputs use global exact-text deduplication, modeling successful persistent-cache reuse. Concurrent duplicate cache misses can increase its cold calls up to the emitted chunk count. Thus the Descry unique count is a cold-call lower bound, not an observed inference counter. Tokens use each implementation's own tokenizer and include special tokens. These counts describe the work each implementation feeds to the model, not equal representations of source code.

The older Descry mode requests roughly 43% fewer model inputs and 49% fewer tokens than Mimirs. It emits an entire declaration as a chunk, then the tokenizer truncates its embedding to 256 tokens. In the audit, 20,123 unique declaration texts exceeded that limit. Their remaining text is still stored and available to lexical retrieval, but does not participate in that embedding. Mimirs instead uses overlapping 256-token windows with the path repeated and averages the resulting vectors. See [declaration chunking](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/chunk/ast.go#L29-L69), [truncation](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/embed/wordpiece.go#L71-L82), and [Mimirs windows](../../../src/embedding/ts_v2.rs).

Current Descry instead estimates a 220-token budget and splits oversized declarations at statement boundaries, with statement overlap and repeated metadata. It requests roughly 36% more unique model inputs and 54% more tokens than Mimirs in this audit. Its estimate is not an exact token guarantee; 9,189 unique texts still exceeded 256 actual tokens and would be truncated. See [defaults](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/chunk/ts.go#L72-L93) and [window construction](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/chunk/ts_assemble.go#L228-L263).

These are input-count differences, not measured speed or retrieval-quality differences. Token lengths affect computation differently, and CPU, runtime and model export also matter. Adopting truncation would change our accepted retrieval policy and requires quality evaluation.

## Runtime, caching and pipeline differences

- Descry defaults to fp32 MiniLM. Its optional q8 export has exactly the same model revision and SHA-256 as ours. Switching to q8 is therefore not a new optimization available to Mimirs. See [model definitions](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/embed/fetch.go#L29-L48).
- Descry's auto-provisioned ONNX Runtime is 1.27.1; an environment override or system install can select another runtime. Mimirs pins 1.22.0 for TS v2 vector compatibility. A newer runtime is a testable candidate, not evidence of a gain. Tokenization and pooling also differ, so identical q8 weights alone do not establish vector equality. See [runtime resolution](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/embed/ortlib.go#L21-L54) and [our parity contract](../port/CONTRACT.md).
- Descry persists embeddings in a separate SQLite cache keyed by embedder identity and hash of exact embedding text. Clearing the search index preserves that cache. This can reduce rebuild and edit costs sharply; there is no evidence that the reported 11-minute run used a warm cache. Our fresh benchmarks use new indexes without previously cached vectors. Within a cold corpus, the audit found only two repeated texts in declaration mode and 1,613 in current tree-sitter mode. See [cache lookup](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/embed/cache.go#L68-L86) and [cache wiring](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/cmd/descry/main.go#L293-L296).
- Descry finishes walking and chunking before embedding, then stores all chunks in one transaction. It does not overlap all the indexing stages. Its embedding concurrency is the relevant parallelism. Our measurements already place 98.819% of embedding-worker active time inside ONNX Runtime. See [Descry stages](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/internal/index/index.go#L67-L97) and [our measured costs](../staged/EMBEDDING-COSTS.md).

The external benchmark pins Kubernetes `70d3cc986aa8221cd1dfb1121852688902d3bf53` and declares pkg, staging/src/k8s.io and plugin subtrees. Our corpus pins `9fa4c1cfa3d761fad081ef413d0dc0f88b5569a9` and its own frozen Go-file manifest. Descry's README says its recent chunker comparison used the whole checkout. Neither published scope identifies the 11-minute run. See [external corpus specification](https://github.com/jKiler/codesearch-bench/blob/94fee7e1cdf249591e711f4c8fdc3ebfff60af35/protocol/corpora.json) and [Descry's comparison note](https://github.com/jKiler/descry/blob/f0a4966b71c25db7d016c9885121fad34d97382d/README.md#L172-L177).

## Recommended next measurements

1. Run the unchanged Rust embedding policy on our frozen Kubernetes corpus with six workers. Compare all published tables and vector bytes with the retained accepted index. This tests the improvement already validated on development corpora.
2. Isolate shared-session execution against independent sessions on the same token tensors, runtime and worker count. Compare memory, throughput and vector equality before considering adoption.
3. Test ONNX 1.27.1 separately on those same inputs. A vector change needs an explicit parity/quality decision, even if runtime improves.
4. Add persistent exact-input caching as a separate change for rebuilds and edits. Track cache hits and model calls so fresh-index timing remains distinguishable from cache-assisted rebuilds.

Given the July 21 date, declaration mode is the likely historical case. Repeat the comparison with matched input texts before treating its wall time as a throughput target. If it used current tree-sitter mode with three workers, the matching configured CPU budget rules out higher worker count as the explanation. Hardware/runtime differences and session sharing deserve investigation first. Do not change chunking just to reduce a timing number without checking retrieval quality.

## Reproduction and retained evidence

[workload.json](workload.json) records revisions, file verification, input counts and the capture's alias mapping. [count-probe.go](count-probe.go) calls Descry's real walker, chunker and tokenizer without constructing a model or writing an index. To reproduce, copy it into `cmd/analysis-count/main.go` in a disposable clone pinned to the inspected commit, then run `go run ./cmd/analysis-count /absolute/path/to/frozen/corpus` from that clone. Building downloaded Go 1.26.2 and module dependencies; no ONNX assets were downloaded by the counter.

The existing Rust runtime probe reconstructed the window population from the retained restored Kubernetes index. Its fixed corpus labels were mapped through explicit temporary symlinks: `mimirs` means Kubernetes in this one audit; both other labels point to the small Mimirs corpus. Only the first population is used above. The probe also performed its normal three sampled reference embeddings plus model initialization. It did not reindex Kubernetes. Raw capture, alias map and config remain under `/tmp/mimirs-descry-workload-audit`; the inspected Descry clone and raw count JSON remain under `/tmp/descry-analysis-20260907`.

The diagnostic scan times in the JSON include extra untruncated tokenization and hashing. The two audits ran concurrently. Those durations must not be presented as production parsing benchmarks. No product defaults or production source were changed by this analysis.
